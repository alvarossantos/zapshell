# Projeto 1.1 — Integridade e concorrência do perfil — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Garantir exclusão mútua real do perfil entre app, backup e restauração, rejeitar `tar` encerrado por sinal e eliminar colisão de temporários de backup.

**Architecture:** Um único `flock` em `<socketPath>.lock` passa a ser adquirido também por backup/restauração via `acquireMaintenance()`, depois do IPC e da espera pelo socket. RAII por escopo libera o fd antes do relançamento. `acquire()` ganha orçamento de espera explícito, aplicado só ao startup.

**Tech Stack:** C++17, Qt6 Core/DBus/Widgets/WebEngine ≥ 6.10, `flock(2)`, `QTemporaryFile`, `QElapsedTimer`, CMake/CTest, makepkg/namcap.

**Spec:** `docs/superpowers/specs/2026-11-23-project1.1-profile-integrity-design.md` (commit `97dff07`)

## Global Constraints

- HEAD de referência: `9c4a0ab`; spec autoritativa: `97dff07`; escopo restrito a ZS-01, ZS-02, ZS-03, ZS-05.
- C++17, Qt6 WebEngine ≥ 6.10; compatibilidade Arch/CachyOS/Wayland/Hyprland. **Nenhuma dependência nova.**
- `void ensurePrivateDir()` + `qWarning()` permanecem (ZS-04 fora de escopo).
- fd de lock usa `O_CLOEXEC`; arquivo `.lock` nunca é removido; inode permanece estável.
- Ordem obrigatória: IPC → `waitUntilReleased()` → `acquireMaintenance()` → manutenção → liberação → relançamento.
- `waitMs = 0` é o padrão de `acquire()`; `15000` apenas no caminho de inicialização em `App::run`.
- Timeout usa **um** `QElapsedTimer` por tentativa de aquisição (orçamento total, nunca reiniciado por retry).
- Instância viva e responsiva não espera: `send()` responde antes de qualquer `acquire()`.
- Nenhum acesso ao perfil após falha de aquisição do lock; ausência do socket nunca é prova de disponibilidade.
- `backupName(now)` (segundos) preservado; publicação final via `::rename()` atômico; **sem promessa de durabilidade**/`fsync`.
- Limpeza de `.partial`: só o legado determinístico `<archive>.partial` e o temporário da própria operação. Nunca varrer `*.partial`.
- `QProcess::NormalExit` **e** `exitCode() == 0` são obrigatórios para sucesso do `tar`.
- Relançar após falha somente se o perfil estiver íntegro e a app estava ativa; rollback não confirmado ⇒ não relançar; nunca iniciar instância extra se outra já responde.
- Testes apenas com `QTemporaryDir` + `XDG_DATA_HOME`/`XDG_CACHE_HOME`/`XDG_RUNTIME_DIR` descartáveis; `QT_QPA_PLATFORM=offscreen`.
- Sem `sudo`, `pacman -U`, `systemctl`, restart do app real, push, merge, flags do Chromium, mídia, CDNs ou mudança de dependências sem aprovação explícita.

## Review Focus

- **App viva pedindo backup:** deve encerrar, liberar o fd e só então a manutenção adquirir o lock — nunca travar 15 s. Teste: `relanceAfterMaintenance` (Task 4).
- **Outra instância ganha o lock entre `waitUntilReleased()` e `acquireMaintenance()`:** manutenção deve aguardar com orçamento e abortar sem tocar o perfil. Teste: `shutdownToMaintenanceContention` (Task 4).
- **`tar` morto por sinal:** deve ser tratado como falha, com temporário removido e archive anterior intacto. Teste: `tarCrashIsRejected` (Task 2).
- **`.partial` legado + backups no mesmo segundo:** legado removido, temporários exclusivos, substituição final atômica documentada. Testes: `stalePartialIsNotLeftBehind`, `concurrentBackupsDoNotCollide`, `sameSecondBackupReplacesAtomically` (Task 3).
- **Falha de restauração com rollback não confirmado:** perfil anterior preservado e nenhum relançamento automático. Teste: `restoreFailureDoesNotRelaunch` (Task 4).

## Rollback strategy

- Cada tarefa é um commit isolado; revert de código = `git revert <commit>` da tarefa ofensora (ou `git reset --soft HEAD~1` se ainda não publicado), seguido de build + suíte completa.
- Nenhum teste toca o perfil real: rollback de dados não é necessário. Perfil, cache e backups originais permanecem intactos.
- Se `makepkg`/`namcap` falhar, **não instalar**; `/usr/bin/zapshell` permanece no binário atual até autorização de `pacman -U`.
- Ordem de recuperação: Task 4 → Task 3 → Task 2 → Task 1 (a última a ser revertida é a base de API).
- Push e merge ficam **fora** deste plano; somente após aprovação explícita e re-verificação do estado.
